# Access Control guide

This guide describes `CM-Chenqf/headplane-zh-cn` on `main`. The development branch does not publish Docker images; use stable release `v0.8.2-zh` with image tag `v0.8.2` for deployment. See [Language and maintenance](/features/language) for release status.

### Permissions and storage

Select **English** and open **Access controls**. Owners, admins and network
admins can write policy; other roles with read permission can inspect it.
Saving requires Headscale `policy.mode: database`. File policies remain
read-only. A missing configured policy file receives a specific explanation;
other load failures do not become empty editable policies.

### Rules, tags and groups

The **Rules** tab edits five sections:

| List           | Policy key      | Behavior                                                                                    |
| -------------- | --------------- | ------------------------------------------------------------------------------------------- |
| Access rules   | `acls`          | Sources, destinations and an optional protocol. A destination without a port receives `:*`. |
| Grants         | `grants`        | Separate sources, destinations, IP protocols/ports, and optional `via` tags.                |
| SSH rules      | `ssh`           | Sources, destinations, Unix users, `accept` or `check` action, and check period.            |
| Hosts          | `hosts`         | Named IP addresses or CIDR ranges.                                                          |
| Auto approvers | `autoApprovers` | Automatic approval of advertised subnet routes and exit nodes.                              |

Grants require Headscale {versions.headscale.grants} or newer and remain hidden
and server-rejected on older versions. Their `via` field only accepts tags;
use `autogroup:internet` for exit-node destinations. Existing app capabilities
are preserved and edited only in the file. Unknown rule actions remain
unchanged, rather than becoming `accept`.

**Tags & Groups** edits `groups` and `tagOwners`. Names start with `group:` or
`tag:`, followed by lowercase letters, numbers or hyphens. Duplicate names
are blocked. User references use `username@`. Tags show current machine usage;
declare a machine's tag in `tagOwners` before relying on it in a rule. Check
references after renaming or deleting a named entry. The Users page writes group
membership to the same policy.

### File editing and saving

Dialog updates change the local draft. **Edit file** and **Preview changes**
share that draft with the structured editors. **Save** sends it to Headscale;
**Discard changes** restores the loaded server policy.

The file editor localizes status, syntax diagnostics and locations, formatting,
search, replace, go-to-line, fold and related controls. Switching language
preserves the policy buffer. Local syntax errors prevent saving. Headscale
validation failures retain original diagnostics, with a Chinese explanation
and HTTP status in Chinese mode. Rejected changes leave the stored policy alone.

**Format** uses two-space indentation and keeps comments, line breaks and
trailing commas. Structured edits regenerate policy text and drop comments,
with a warning. Use the file editor to preserve comments. Unknown top-level
fields such as `nodeAttrs` and `tests`, and extra rule fields, retain upstream
round-trip behavior. Commands, identifiers and user-supplied values are not
translated.

**Preview rules** remains an unavailable upstream feature, with a translated
notice. It does not simulate connectivity.

### Configuration examples

# Headscale config.yaml

  mode: database
